# Provider development

`apps/server/src/providers/types.ts` is the extension point. `Workspace` owns the persisted setup state, explicit demo/hardware choice, and transitions between them. `Service` owns persistence, mode isolation, file lifecycle, concurrency, and public job state. Print jobs retain the normalized PDF for seven days for previews, even when submission is unconfirmed; deleting a job removes its document. Preview-only requests never submit a job or persist a draft. Providers own device discovery, backend configuration, actual execution, and status interpretation.

`host-discovery.ts` optionally merges fresh macOS Bonjour snapshots into hardware discovery results. The native host helper uses Network.framework and exports advertised, TCP-resolvable IPv4 IPP/IPPS printers and eSCL scanners. The server revalidates addresses, size, schema, timestamp and source. `hostDiscovery` in the result records the source and refresh time for the UI. The demo provider never reads these files. Missing or expired snapshots produce a visible warning and cannot configure devices.

| Method                                                  | Contract                                                                                                                                                                      |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `discover()`                                            | Return candidate `DeviceInput[]` plus partial-failure warnings; finding a device is not a successful health probe                                                             |
| `add(input, id)`                                        | Validate/probe a target; return the configured device with a real backend target                                                                                              |
| `inspect(device)`                                       | Return available capabilities and truthful state; use `unknown` when unreachable/unconfirmed                                                                                  |
| `print(device, path, title, options)`                   | Submit the normalized PDF exactly once; return the external job ID                                                                                                            |
| `poll(job, device)`                                     | Map backend state explicitly; never infer completion from disappearance                                                                                                       |
| `cancel(job, device)`                                   | Ask the real backend to cancel; throw on rejection                                                                                                                            |
| `scanSources(device, source?)`                          | Return source names, feeder flags, duplex availability, and resolution/color constraints for the selected source                                                              |
| `scan(device, outputPath, options, pageLimit, signal?)` | Write one real PNG, or numbered PNGs using the supplied `%d` batch pattern, within the private directory; respect the remaining page limit, timeouts, and cancellation signal |

Scans retain private original page PNGs plus a generated PDF and first-page preview. Optional `scanPages`, `scanDirectory`, `scanWorkPath`, and `scanRevision` fields extend existing job JSON compatibly. Public serialization exposes page IDs, rotations, and optional crop rectangles, never paths. Crop coordinates are finite integer pixels `{ x, y, width, height }` measured from the top-left of the original unrotated PNG. The server validates non-empty bounds against that image, extracts the crop before applying clockwise rotation, and regenerates exports from the unchanged original. Omitting `crop` resets it. New pages record their acquisition `resolution` (DPI) privately in `scanPages`. PDF dimensions use original pixels × 72 / DPI, so A5, A4, Letter, and cropped pages retain their physical scale without added margins or an A4 size limit. Rotation changes the displayed orientation; edits and mixed-resolution appends retain each page’s own DPI. For legacy pages without recorded DPI, valid image density metadata (1–9600 DPI) supplies the scale. If neither is available, the original image is fitted into a 595.28 × 841.89 point A4 rectangle as before, and crops retain that scale. Job-level options are never used to guess legacy DPI because they may describe a later append. Existing PDFs change only when pages are edited or appended. The page image endpoint returns the original by default; `?rendered=1` returns the cropped, rotated preview. Legacy one-page jobs derive their page from the original preview and remain editable. Appends and edits publish new document files before replacing the stored revision; stale revisions and concurrent changes are rejected. Failed or interrupted follow-up operations preserve committed pages. Retention, deletion, and demo removal clean up page originals and working directories as well as exported files.

Real scan output uses a validated, writable absolute server root configured during setup or in Settings. Each job captures its paths when created; changing the root does not relocate existing files. Demo scans stay in instance storage.

Printing capabilities expose `sides` as the supported subset of `one-sided`, `two-sided-long-edge`, and `two-sided-short-edge`. Missing `sides` means discovery is unavailable; an empty array means no application-supported sides were advertised. Never infer one binding edge from the other. The UI reconciles selections when capabilities change, and submission always re-inspects the printer and checks the exact side before retaining or sending a document. Existing job options remain unchanged; saved demo devices rebuild their capabilities on inspection after an upgrade.

Print options optionally record `pageRanges` (comma-separated positive page numbers and ascending inclusive ranges, up to 2000 characters) and `pageParity` (`all`, `odd`, or `even`). Omitted ranges select the whole normalized source; an explicitly empty range is invalid. Bounds are checked against the source PDF before parity filtering. The filter uses original one-based page numbers, duplicates are removed, and pages retain document order. A selection must contain at least one page. Uploads and saved documents use the same service validation and page extraction before any job/file is retained or submitted. The retained PDF contains exactly the selected pages, preserving page dimensions and rotations; copies and duplex settings are passed through normally. Providers receive this PDF with range/parity fields removed, so they must not apply selection again. Duplex pairs consecutive selected pages, without placeholders for skipped source pages; an unpaired final page has a blank back. This is not manual duplex imposition. Reprinting a retained selection starts with all pages of that retained PDF, numbered from one. Existing persisted options remain valid without a migration. Tests inspect the PDF passed to the hardware provider and its `lp` arguments using stubbed CUPS transport, not physical printer output. No new dependency is required.

Scanner capabilities extend the existing `/api/devices/:id/scan-sources` endpoint; optional `?source=` selects an advertised paper source. `resolutions` is a discrete numeric list or `{ min, max, step? }`; `colorModes` contains exact backend strings, including names such as `Grayscale` and `Lineart`. Optional `defaultResolution` and `defaultColorMode` record the current advertised values. Missing constraints mean unknown; empty lists mean no selectable values within application limits (1–9600 dpi), including inactive or read-only options. Unknown fields use only the explicit 150/300/600 dpi or Color/Gray fallback; they never imply verified support. A discovery failure returns a curated `warning`, without backend diagnostics. Source-specific queries run with the validated advertised source before `--all-options`; a failed source query does not reuse default-source constraints. Submission rechecks capabilities inside the scanner's existing acquisition lock before invoking the actual scan command. Invalid selections fail the job, preserving existing pages on append. Demo capabilities are fixed and enforced as well. Fixtures cover these contracts, not physical compatibility. Backends exposing only separate X/Y resolution options or unparseable constraints use the unknown fallback; other option dependencies beyond paper source remain subject to backend validation. No new runtime dependency is required.

Capability reads are cached in SQLite settings per mode, configured scanner target, and paper source. Adding a scanner warms the default and each advertised source sequentially. Existing installations discover missing entries on demand. Known results, including empty selectable lists, survive server restarts; unknown, partial, or failed results are retried on the next read. Concurrent reads of one entry share the same request. The dialog uses these stored values and offers **Refresh scanner settings** (`?refresh=true`) to invalidate that scanner's entries and query the selected source again. A failed refresh removes stale values rather than reporting them as current. Removing devices/demo data clears the associated records; generation and target checks prevent obsolete requests from restoring invalid entries. Shutdown drains pending lookups. Acquisition bypasses this configuration cache and always revalidates using the provider. Existing settings storage is reused without a schema migration or new runtime dependency.

## Adding an integration

1. Keep it in a separate provider module. Select it in the server factory through trusted startup configuration, never through arbitrary client-supplied executable names.
2. Reuse existing Zod/shared contracts where applicable. Extend those contracts and UI capabilities together if a new feature needs more than the standard paper/color/duplex model.
3. Use a maintained protocol library or system tool. `command.ts` uses `execFile` with no shell, output limits, locale stability, and timeouts. Validate addresses and generated queue names independently of escaping.
4. Add failure-path tests and fixtures for the actual library representation. IPP enum values may be decoded to strings (`completed`, `idle`), not numbers.
5. Document platform dependencies, licensing, privileges, network boundaries, and hardware verification status.

The current combined hardware provider delegates printing to CUPS and scanning to SANE. Only the demo provider generates output. Production code has no fallback to that provider. The server persists mode on every device and job and filters all lookups to the persisted active mode. Fresh installations seed nothing until the user explicitly chooses the demo. Removing demo data blocks new operations, drains running demo work, and deletes only demo records and their referenced files before starting hardware setup.

`cupsIpp()` queries the local scheduler; arbitrary client-controlled IPP hosts are not passed to the Node HTTP client. New printer URIs go to CUPS after validation; reaching LAN devices is an intentional administrator capability. Discovery advertisements are untrusted and must pass the same checks as manually entered addresses.

## Persistence and failures

Device-status reads are owned by the server: concurrent snapshot requests share one in-flight inspection of the configured devices, and completed results are reused for five seconds. The next request at or after expiry waits for a new check; there is no background refresh timer. `devicesCheckedAt` in the snapshot records when that set of checks completed, not when the browser fetched it. Jobs are read afresh on every snapshot. Adding or removing a device invalidates the cached device state, including pending results; obsolete checks cannot repopulate the cache. Caches are isolated by mode. Mode transitions drain pending snapshots before switching; demo removal and shutdown drain inspections and discard cached results. This cache is only for snapshots; print submission still checks current capabilities directly.

Inspection failures replace healthy cached state with `unknown`, without stale capabilities, and a curated warning. Providers may also return an explicit unknown state and their own safe explanation. These results have the same five-second lifetime, allowing the next refresh to recover without exposing backend diagnostics.

The SQLite schema is managed in `store.ts` with `user_version=2`, WAL mode, parameterized statements, and a busy timeout. The version-2 migration preserves legacy credentials in the users table and revokes legacy sessions; new databases start without accounts. A future incompatible schema change must ship an explicit versioned migration; do not silently reinterpret existing JSON fields. Public job serialization strips internal file paths and external job IDs.

History uses `GET /api/jobs?limit=30&kind=scan&filter=all` (`kind` is optional; `filter` is `all`, `active`, or `completed`; limits are 1–100). Responses contain `jobs`, the total matching record count (`total`), the current cursor position (`offset`), and an optional opaque `nextCursor`, passed back as `cursor` with the same mode and filters. A separate SQL aggregate counts matching records and their position before the cursor without loading historical job JSON; this keeps displayed ranges accurate when records are inserted or deleted. SQLite fetches at most the page size plus one, using indexes ordered by `(created DESC, id DESC)`. Cursors carry the last ordering tuple, so inserts and deletion of the cursor's record do not shift older pages. Listings remain live rather than frozen snapshots: revisit the first page for new records, including jobs that have changed status. Snapshots retain a bounded latest-200 query for overview activity; scan dialogs poll `GET /api/jobs/:id` so older documents stay reachable. File retention is independent of history pagination, and `hasFile` continues to describe retained document availability.

A print transport error can happen after the scheduler accepted a job. Store `unknown`, keep a clear error, and never retry automatically. Queued/processing scan jobs are marked failed after restart when no committed document exists; interrupted appends/edits keep the prior document and report the interruption; interrupted unconfirmed print submissions remain unknown. Already submitted CUPS print jobs continue to be polled after restart.

Scanner concurrency is per configured device ID. Two aliases for the same physical scanner can bypass that logical lock; backends must still handle device-busy errors. Distributed workers are outside the MVP.

## Scan cancellation

`POST /api/jobs/:id/cancel` also cancels active acquisitions. The service owns an `AbortController` per acquisition and awaits the provider task before releasing the scanner/job locks and deleting working files. Providers must propagate the optional signal through capability probes and acquisition, and settle only after their process has stopped writing. SANE sends SIGTERM, escalates to SIGKILL after one second if needed, and waits for process closure. Cancellation does not expose command stderr. Document edits are not acquisitions and cannot be canceled through this endpoint.

All unpublished pages from the operation are discarded, including complete new feeder images. Previously published originals, page IDs, revision, PDF, and preview survive and remain downloadable even during an append. A first acquisition becomes `canceled` with no file; an append returns to `completed` with the saved document and an explicit cancellation message. A signal check immediately before synchronous publication decides the race: cancellation before it discards the new revision; cancellation after it returns the completed revision without changing its status. Repeated cancel requests on a terminal scan return the current result. Closing the dialog only stops browser polling and leaves acquisition running; active jobs can be reopened to cancel explicitly. Shutdown and demo removal still drain tracked tasks, including cancellation cleanup.

Controlled tests cover cancellation during source probes, acquisition and PDF export, delayed provider shutdown, child termination/escalation, saved-document downloads, retries, and late completion. Browser API fixtures cover closing/reopening, the cancel action, saved-page visibility, and stale polling responses on desktop and mobile. These do not certify physical eSCL/WSD/USB abort behavior or that a feeder stops moving immediately; that requires device-specific hardware validation. No new dependency or schema migration is required.

## Verification boundaries

Unit/integration tests use injected command and IPP request functions. A local HTTP IPP fixture additionally exercises real library serialization/parsing. Browser tests use the explicit demo provider and real document conversion. CI container tests verify daemon startup without hardware. Only a report from an actual device should be described as hardware-tested.
