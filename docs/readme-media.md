# README media maintenance

The README uses recordings of the production frontend with the real local API and
**simulated demo devices**. These demonstrate software workflows, not physical
printer/scanner compatibility. Sample PDFs are generated by the capture script;
scan pages come from the project's demo provider. Both are project-owned content
under the repository's MIT license. No user documents, accounts, or external media
are needed.

## Regenerate

Use the supported Node/npm version from [Contributing](../CONTRIBUTING.md).
Install FFmpeg with `ffprobe` on your PATH (for example, `brew install ffmpeg` on
macOS or `sudo apt install ffmpeg` on Debian/Ubuntu), then:

```sh
npm ci
npx playwright install chromium
npm run demos
```

This rebuilds the application and runs `scripts/capture-screenshots.mjs
--animations`. The existing screenshot runner creates a disposable database on a
random loopback port, chooses **Try demo** through the UI, then calls
`scripts/capture-demos.mjs`. It never connects to a running installation or to real
hardware. Temporary WebM recordings, downloaded PDFs, and application data are
removed on normal completion or an error. A forcibly terminated process may leave
an `openwebprint-screenshots-*` directory in the OS temporary directory; remove it
once its process has stopped.

The two English/light-theme recordings use a **1200 × 1000 CSS-pixel viewport**
and device scale 1. Playwright records at the same dimensions. Actions use semantic
labels, real uploads/downloads, and deliberate reading pauses. Hover/focus shows
the interaction target; no artificial cursor, mock UI, or replacement server
responses are added. Slow operations finish before the next action, so duration
and exact bytes can vary between machines. The script checks the print job reaches
Completed and the exported PDF has two pages with the edited rotation/order. It
also fails on browser JavaScript errors.

Final assets live in `docs/images/`:

- `demo-print.gif`: upload, preview, page range and duplex selection, job status.
- `demo-scan.gif`: scan, append, rotate, reorder, download a multipage PDF.
- `demo-print-still.png` and `demo-scan-still.png`: static alternatives from the
  same journeys, linked alongside each animation.
- `demo-metadata.json`: measured dimensions, frame count, duration, and exact bytes,
  regenerated with the clips.

Run `npm run screenshots` separately to refresh the original 1440 × 1000 overview,
print, and scan screenshots. This retains the existing static capture workflow.
Do not commit WebM intermediates or private application data.

## Format and optimization

GIF is used as an ordinary Markdown image, so the demo is visible inline in the
README without a video player or a third-party host. Each clip **plays once**;
open it and reload to replay. It does not automatically repeat while someone reads
the rest of the page. The GIF file itself has no pause controls or reduced-motion behavior. In our
GitHub review, the rendered README added its own play/pause and open-image
controls. Other Markdown viewers may not, so every clip also has a descriptive
text sequence and a linked still. There are no flashes or decorative transitions.

MP4/WebM offers better compression and playback controls, but a repository video
link does not replace an inline Markdown image. GitHub-hosted video attachments
also require a separate upload workflow. Animated WebP/APNG can preserve finer
color, but offer no playback-control advantage here. We retain GIF for its simple
repository-owned image embedding and verify the actual GitHub rendering rather
than relying on a local Markdown preview.

The local conversion is equivalent to:

```sh
ffmpeg -y -i recording.webm -filter_complex \
  '[0:v]fps=8,split[a][b];[a]palettegen=max_colors=128:stats_mode=diff[p];[b][p]paletteuse=dither=bayer:bayer_scale=3:diff_mode=rectangle' \
  -loop -1 docs/images/demo-print.gif
ffprobe -v error -show_entries format=duration:stream=width,height,nb_frames \
  -of json docs/images/demo-print.gif
```

Eight frames per second, a 128-color palette, and rectangle differencing reduce
weight while retaining readable UI text. Native dimensions allow opening the
image for details on a small screen. Aim for roughly 10–20 seconds per clip;
allow a little more time for a real job to finish. Keep the two GIFs together below
8 MiB; review the generated metadata before committing. No new npm dependency is
required. Playwright is already a development dependency (Apache-2.0); FFmpeg is
an optional local tool, not redistributed by this change. Its license depends on
the installed build (LGPL/GPL); inspect `ffmpeg -L` for that build's terms.

## Review before publishing

1. Play both clips from beginning to end. Check pacing, legible labels, demo
   notices, page edits, and the final job/download result. Review both stills.
2. Check `demo-metadata.json` against `ffprobe` and file sizes. If a clip becomes
   large, shorten idle pauses or lower the frame rate before reducing resolution.
3. Run `npm run check` when capture code changes. Run both capture commands to
   verify the shared runner. Check formatting and local Markdown links.
4. Push the dedicated branch, open its README **on GitHub**, and check desktop
   (1440 px) and mobile (390 px), in light and dark color schemes. Verify both GIFs
   load at their native aspect ratio, the logo remains visible, captions wrap
   without horizontal overflow, and static/full-size links work. On mobile the
   caption explains the workflow; open the original image for small UI labels.
5. Include screenshots of that actual GitHub rendering and direct links to both
   animations in the PR's **Proof of Done**. Record remaining limitations honestly.

they are PR evidence, not part of the README's media download weight.
